# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Spring Boot 3.3.5 (Java 17) REST backend for a veterinary appointment app ("Proyecto integrador del 311 de tecnología en sistemas"). Domain language, SQL, logs and error messages are in Spanish; method/endpoint names are a mix of English and Spanish.

## Commands

Use the Maven wrapper (`mvnw.cmd` on Windows, `./mvnw` in Git Bash):

- Build: `./mvnw clean package` (add `-DskipTests` to skip tests)
- Run: `./mvnw spring-boot:run` (serves on port 8080)
- All tests + coverage report: `./mvnw verify` (the notes after the Security section say which tests need a DB or Docker)
- Single test: `./mvnw test -Dtest=ProyectoIntegradorApplicationTests` (or `-Dtest=Class#method`)

The local machine runs JDK 23, where javac no longer runs annotation processors by default; `pom.xml` sets `maven.compiler.proc=full` so Lombok still works. Don't remove it — without it the build fails with hundreds of "cannot find symbol" errors (`log`, getters/setters).

### Security (package `security/`)

- Stateless JWT auth (JJWT, HMAC-SHA256). `POST /integrador/login` returns `token` and `expiresIn` at the top level of `ResponseLogin` (next to `responseObj`). Every other endpoint except `login`/`register` requires `Authorization: Bearer <token>`; the SSE endpoint also accepts `?token=` because browser `EventSource` can't send headers.
- Endpoints still receive client ids in their DTOs, but controllers call `SecurityUtils.requireSameClient(...)` (and `requireSameUsername`) *before* their `try/catch` so the `AccessDeniedException` reaches `GlobalExceptionHandler` (403, code `6619`). Do the same in new endpoints that take a client id. Missing/invalid token → 401, code `6618` (written by `SecurityConfig`). Unlike other errors these use real HTTP status codes.
- Config: `jwt.secret` / `jwt.expiration-minutes` / `app.cors.allowed-origins` in `application.properties`, overridable by env vars `JWT_SECRET`, `JWT_EXPIRATION_MINUTES`, `CORS_ALLOWED_ORIGINS`.
- `@WebMvcTest` tests must `@Import({SecurityConfig.class, JwtService.class})` and send a token from `jwtService.generateToken(...)`, otherwise Boot's default security applies.
- Roles (`security/Role`: ADMIN, VETERINARIO, CLIENTE) are resolved from `rol.descripcion` text (contains ADMIN / VETERIN / MEDIC), never by hardcoded `rol_id`; unknown or null → CLIENTE. The role is a `role` claim in the JWT, a `ROLE_*` authority, and `InfoUser.role` in the login response. `requireSameClient`/`requireSameUsername` let ADMIN and VETERINARIO act on any client; `requireOwnClient` is strict (used for the SSE channel). `@EnableMethodSecurity` is on, so admin-only endpoints use `@PreAuthorize("hasRole('ADMIN')")` (see `VeterinarianController`). A controller interface with `@PreAuthorize` must also carry `@RestController` (as all controller interfaces here do), otherwise the security proxy isn't detected as a handler and every route 404s.
- Veterinarians (VET-01): a vet is a `cliente` row (login, role VETERINARIO) + `personal` (linked via `personal.cliente_id`) + `medico` (`identificacion_medico` = `personal_id`); `medicoId` is what appointments use. Inactive staff (`personal.activo = false`) can't log in, aren't offered in the selector and can't be booked.
- Vet agenda (VET-02): `GET /integrador/agendaCita/veterinarian?fecha=yyyyMMdd` (`@PreAuthorize` VETERINARIO/ADMIN on the interface method). A vet's `medicoId` is resolved from the token user via `personal.cliente_id`; a vet asking for another `medicoId` gets 403, an ADMIN must pass `medicoId`. When a service throws `AccessDeniedException`, the controller must rethrow it from its `catch` (see `AgendaControllerImpl.getVeterinarianAgenda`) or it gets turned into a 200 error envelope.
- Appointment status (VET-03): `PATCH /integrador/agendaCita/{agendaId}/status` with `{estadoId}` (vet: own appointments only; admin: any). States are recognized by `estado_cita.descripcion` text via `enums/AppointmentStatus` (same idea as `Role`), and allowed transitions live in `AppointmentStatus.canTransitionTo`. The update is conditional on the current `estado_id` to avoid overwriting a concurrent change. Requires `sql/VET-03_estados_cita.sql` (creates Confirmada / Atendida / No asistio if missing). Never hardcode `estado_id` values: look them up with `AgendaCitaRepository.findEstadoId(AppointmentStatus)`.
- Scheduling/cancel/reschedule (VET-04): new appointments always start as PROGRAMADA (the client no longer sends `estadoId`); only pending appointments (`AppointmentStatus.isPending`) can be cancelled or rescheduled; `PATCH /integrador/agendaCita/{agendaId}/reschedule` (client: own, vet: assigned, admin: any) sets REPROGRAMADA. Availability is per vet (`isSlotAvailable`: no other non-cancelled appointment within `APPOINTMENT_MINUTES` = 30), dates in the past are rejected, and the pet must belong to the client. Requires `sql/VET-04_reprogramacion_citas.sql`, whose last query shows how each `estado_cita` row is recognized.
- Pets (CIT-02): `PUT /integrador/pets/{mascotaId}` and `PATCH /integrador/pets/{mascotaId}/status`; `getListPets` returns only active pets unless `includeInactive=true`; inactive pets can't be booked. Requires `sql/CIT-02_gestion_mascotas.sql` (`mascota.activo`). Ownership checks inside services use `SecurityUtils.canAccessClient(user, clienteId)` (pure; staff → any client) instead of the SecurityContext-based `requireSameClient`.
- Owners (CIT-03): `/integrador/clients` — `GET /{id}` and `PUT /{id}` (client: self, staff: any), `GET` list with `includeInactive`/`q` (staff), `PATCH /{id}/status` (ADMIN; not for staff accounts, not for oneself). Owner inactivation uses the existing boolean `cliente.estado_cliente` (NULL = active): inactive users can't log in (`ProyectoRepository.isUserActive`, checked after the password) and can't be booked. Staff accounts also live in `cliente`; "owners" are filtered out from staff by `rol.descripcion`.
- Clinical attention (HC-01): `POST /integrador/clinicalHistory/attentions` (VETERINARIO only, assigned vet) inserts into `atencion_clinica` and moves a pending appointment to ATENDIDA in the same transaction (an appointment already ATENDIDA without a record is also accepted); one attention per appointment (UNIQUE `agenda_id`), not before the appointment day. Clinical history (HC-03): `GET /integrador/clinicalHistory/pets/{mascotaId}` returns the pet plus its attentions (newest first), inactive pets included; it and `GET /attentions/{id}` are readable by staff and by the pet's owner (read-only — the Ley 576 de 2000 reserve is toward third parties), checked with `canAccessClient` on the pet's `cliente_id`. Don't add edit/delete of clinical records. Requires `sql/HC-01_atencion_clinica.sql`.
- Treatments and vaccines (HC-04/HC-05, `TreatmentVaccineRepository`, tables `tratamiento`/`vacuna` from `sql/HC-04_tratamientos_vacunas.sql`): any VETERINARIO registers them for an active pet (optional `atencionId` must belong to the same pet); treatments follow `enums/TreatmentStatus` (EN_CURSO → FINALIZADO/SUSPENDIDO, stored by name, conditional update, `fecha_fin` set to today); vaccines can't be applied in the future and `proximaDosis` must be after the application. `GET /clinicalHistory/vaccines/upcoming?days=30` lists the latest dose per vaccine name whose next dose is overdue or due within `days` (clients: only their pets). The pet history response includes `tratamientos` and `vacunas`.
- Reports (REP-01..03, `ReportController` `/integrador/reports`): `appointmentsByStatus`, `attentionsByVeterinarian`, `attendedPets`, all with `desde`/`hasta` (`yyyyMMdd`, inclusive, max 366 days) and optional `medicoId`; response is a generic `Report<T>` (period, `medicoId`, `total`, `items`) with row records in `models/ReportRows`. Staff only; a vet always gets only their own data (other `medicoId` → 403). `fecha_atencion` is a TIMESTAMP, so the repository filters `>= desde AND < hasta + 1 day`. No SQL script needed.
- API docs (QA-05): springdoc-openapi (`config/OpenApiConfig`, bearer scheme) serves Swagger UI at `/swagger-ui.html` and the spec at `/v3/api-docs`, both permitted without a token in `SecurityConfig`; turn off with `API_DOCS_ENABLED=false`. Controller interfaces carry `@Tag`; public endpoints use `@SecurityRequirements` (empty) to drop the lock icon. `config/OpenApiDocsTest` boots the full context without a DB (DataSource/JdbcTemplate auto-config excluded, `JdbcTemplate` mocked), so it also catches bean-wiring errors.
- Public `/register` always assigns the CLIENTE role (looked up with `getRoleId(Role.CLIENTE)`); staff accounts are created via `/integrador/veterinarians` (ADMIN) or directly in the DB.

Passwords are hashed with BCrypt (`config/PasswordConfig`). Legacy plaintext passwords in `user_credentials.password_hash` are re-hashed on the user's next successful login (`ProyectoServiceImpl.passwordMatches`).

`ProyectoServiceImpl` has a hardcoded demo login (`demo` / `demo123`, ADMIN, user id 0 so it never collides with a real `cliente_id`) marked `TODO: ELIMINAR` — intentional for demos, must be removed before any deployment.

`ProyectoIntegradorApplicationTests` is a `@SpringBootTest` context-load test and needs the real database reachable (the app also won't start without it). Run everything else with `./mvnw verify -Dtest='!ProyectoIntegradorApplicationTests'`:

- Unit tests (`@WebMvcTest` controllers, Mockito services, enums) need nothing.
- `integration/VeterinaryFlowIntegrationTest` (QA-03) runs the whole API flow (register → vet → pet → appointment → attention → treatment/vaccine → reports) against a throwaway PostgreSQL 16 in Docker (Testcontainers + `@ServiceConnection`), built from `sql/schema.sql` + `src/test/resources/integration/seed.sql`. It's skipped (not failed) when Docker isn't available. Seed ids are deliberately non-standard, so code must not hardcode `rol_id`/`estado_id`.
- `sql/schema.sql` is a `pg_dump --schema-only` of the dev DB. When you add a schema-change script to `sql/`, regenerate it (or append the same DDL), otherwise the integration test runs against a stale schema.
- JaCoCo (QA-02): `verify` writes `target/site/jacoco/index.html` and fails if line coverage of `services.Impl` drops below 70 %.

## Database

PostgreSQL, configured in `src/main/resources/application.properties` through env vars `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` (defaults: `jdbc:postgresql://localhost:5432/VETERINARIAPP` and the local dev credentials). Each developer overrides them instead of editing the file. There is no full schema file and no JPA entities. Schema *changes* go in `sql/` (not `db/`, which is gitignored for local DB data) as hand-run SQL scripts named after the Jira issue (e.g. `sql/VET-01_gestion_veterinarios.sql`, which adds `personal.activo` and `personal.cliente_id`); code that depends on them requires the script to have been run. The ER diagram is Figura 2 of the thesis document. The rest of the schema (tables such as `cliente`, `cita`, `agenda_cita`, `estado_cita`, mascota/veterinario tables) lives only in the external database, and table/column names are known only from the SQL strings in the repository classes.

## Architecture

Layered: `controllers` → `services` → `repository`, with every layer split into an interface plus an `Impl/` subpackage class.

- **Controllers**: Routing annotations (`@RequestMapping`, `@GetMapping`, `@Valid`, etc.) are declared on the **interface** (`controllers/*Controller.java`); the `Impl` class only carries `@RestController` and implements the methods. Add new endpoints to the interface first. All routes are under `/integrador/...`. GET endpoints bind query params via `@ModelAttribute` DTOs; POST/PATCH use `@RequestBody`.
- **Response envelope**: Every endpoint returns `ResponseEntity<ResponseGeneric>` (`responseCode`, `responseDesc`, `responseObj`). Codes come from `enums/CodesResponse` (`"0000"` = OK). Errors are caught in the controller and returned with **HTTP 200** and an error code, with `ErrorMessages.clientMessage(e)` in `responseObj` — the client distinguishes success by `responseCode`, not HTTP status. Never put `e.getMessage()` in a response (RNF-05): only `BusinessException` messages reach the client; any other exception is logged and replaced by a generic message. So in services throw `BusinessException` for user-facing messages ("No hay disponibilidad de citas") and plain `RuntimeException` for internal failures. Uncaught exceptions are handled by the catch-all in `GlobalExceptionHandler` (code `6620`, keeps Spring's 4xx statuses, 500 otherwise). Follow this pattern and add new codes to `CodesResponse`. Bean Validation failures (`@Valid` on `@RequestBody`/`@ModelAttribute`, malformed JSON, a path/query param of the wrong type such as `/pets/abc`, a missing required `@RequestParam`) happen before the controller and are turned into the same envelope with code `6617` by `exceptions/GlobalExceptionHandler`. In DTOs use `@NotBlank` only on `String`; numeric fields are `Integer` with `@NotNull`/`@Positive` (a primitive `int` defaults to 0 and `@NotBlank` on it throws at runtime).
- **Services**: Business validation is done by calling repository checks that return `Optional` and chaining `.orElseThrow(() -> new BusinessException("..."))`; that message becomes the client-facing error. Beware the `Optional<Boolean>` trap: `Optional.of(false)` does not trigger `orElseThrow` — return `Optional.empty()` for "not valid".
- **Repositories**: Plain `JdbcTemplate` with SQL text blocks and inline lambda row mappers (or `utils/ClienteRowMapper`). Methods return `Optional<...>`, catch exceptions internally, log them, and return `Optional.empty()` — so a DB error looks the same as "not found" to the service.
- **Models**: Lombok `@Data` POJOs/DTOs in `models/` (request DTOs are named `Data*DTO`); selector (dropdown) models in `models/selectors/`.
- **Dependency injection**: constructor injection via Lombok `@RequiredArgsConstructor` with `final` fields; logging via `@Slf4j`.

### Real-time notifications (SSE)

`GET /integrador/notifications/connection?client_id=...` opens a Server-Sent Events stream (`NotificationServiceimpl`). Emitters are kept in an in-memory `ConcurrentHashMap` keyed by client id (no timeout, single-instance only). On connect it sends a `conectado` event; `AgendaServiceImpl.scheduleAnAppointment` calls `notifyAppointmentCreation`, which sends a `cita-creada` event with a `DetailAppointment` payload to that client.

### Conventions worth knowing

- Appointment dates/times arrive as strings in `yyyyMMdd` and `HHmmss` formats and are parsed in the service.
